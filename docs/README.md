# Bara Repository Research Report

This is a read-only technical investigation for the six planned Bara changes. No application or backend code, migrations, or commits were created as part of this research.

## A. Executive Architecture Summary

Bara is a Flutter client backed by a Node/Express/Prisma/PostgreSQL service with Redis-backed read caches, durable domain-event and notification projection infrastructure, race-resolution workers, and RevenueCat-backed billing.

The six changes touch four shared domains:

- Race power-up execution, scoring, activity, notifications, and realtime refresh.
- Backend-owned shop/catalog policy plus Flutter store presentation.
- Backend-authoritative Daily Spin selection and reward fulfillment.
- Race participant preferences, especially `favoritedAt`, race lifecycle, and cached race lists.
- Team chat persistence and realtime delivery.
- Bara Gold entitlement, RevenueCat synchronization, rewarded-ad bypasses, and billing credit ledgers.

PostgreSQL is authoritative for durable product state. Redis accelerates reads and invalidation; it is not the sole source of truth. Power-up execution and race mutations use transactional commands with race-scoped locking and resolution queues. Notifications increasingly use durable domain-event projection, while race activity remains a separate persisted event stream.

## B. Change 1 — Decoy Activity Feed

### Current behavior

Race activity is stored in `race_powerup_events` as `RacePowerupEvent` rows containing `actorUserId`, `eventType`, `powerupType`, `targetUserId`, `description`, optional `metadata`, and `createdAt`. The feed merges these system events with `race_messages`. Human-readable descriptions are stored as final text; metadata is only partial structured context.

Notifications are a separate representation and are generated by emitted events and durable domain-event projections. Realtime publication refreshes clients but is not the durable activity source.

### Full execution path

```text
Flutter race-detail power-up UI
 -> POST /races/:raceId/powerups/:powerupId/use
 -> route validation
 -> usePowerup
 -> transaction/race write fence
 -> lock power-up, race, target participant/effect rows
 -> validate target and eligibility
 -> apply effect or penalty
 -> consume RacePowerup
 -> create RacePowerupEvent
 -> emit POWERUP_USED
 -> invalidate race-progress cache
 -> enqueue race resolution
 -> notification projection/handler
 -> realtime refresh
```

`usePowerup.js` passes the original attacker into `consumeDecoy`, then processes redirected landing slots. The consumed power-up stores the resolved target. The final event normally stores the actor and resolved target, but there is no dedicated schema for original target, Decoy owner, redirect recipient, relationship, block result, or scoring outcome.

### Relevant files

Frontend: `lib/screens/race_detail_screen.dart`, `lib/services/backend_api_service.dart`, `lib/services/notification_service.dart`, `lib/widgets/effect_badge.dart`, `lib/widgets/powerup_icon.dart`.

Backend: `src/modules/powerups/commands/usePowerup.js`, `src/modules/powerups/models/racePowerupEvent.js`, `src/modules/powerups/models/raceActiveEffect.js`, `src/modules/powerups/models/racePowerup.js`, `src/modules/powerups/commands/openMysteryBox.js`, `src/modules/powerups/leechTransfers.js`, `src/modules/powerups/constants/powerupPolicy.js`, `src/modules/social/queries/getRaceMessages.js`, `src/modules/social/queries/getRaceMessageStreams.js`, `src/modules/notifications/notificationHandlers.js`, `src/modules/notifications/services/domainEventV1Projection.js`, `src/modules/notifications/services/notificationDelivery.js`, `src/modules/races/services/raceResolutionQueueV2.js`.

`RacePowerupEvent` indexes are `(race_id, created_at)` and `(actor_user_id, event_type, created_at)`. Active effects have unique `(powerup_id, target_participant_id)` and indexes for target/status, race/status, and Decoy cooldown lookup.

### Activity event schema

The schema is partly structured and partly presentation-oriented:

```text
eventType, powerupType, actorUserId, targetUserId, description, metadata
```

The feed intentionally hides `POWERUP_IMPOSTER`, `MYSTERY_BOX_OPENED`, and `POWERUP_REROLLED`, plus selected metadata-marked audit rows. These filters are applied at database query time and defensively again for cached data.

### Notifications/realtime behavior

`POWERUP_USED` is emitted separately from activity persistence. The notification system has durable intents, projections, schedules, delivery claims, push attribution, Redis unread invalidation, and reconciliation jobs. `DECOY_CONSUMED_V1` exists in the projection vocabulary, but compatibility handlers preserve the frozen client’s public `POWERUP_USED` type. Notification suppression or projection failure can make notifications differ from activity. Realtime failure should not delete committed activity, but can delay its appearance.

### Team-race behavior

Targeting uses `Race.isTeamRace`, `RaceParticipant.team`, accepted status, and forfeit state. Activity has no first-class team relationship field. For Team Red A/B and Team Blue C/D, when A attacks C and C’s Decoy redirects to D, the semantic chain is A original attacker, C original target and Decoy owner, D final target, and A remains the effect source. The current schema does not guarantee that all identities survive into every feed or notification representation, creating the risk that text implies C attacked D.

### Why events can be missing or misleading

- Power-up branches construct their own event types and descriptions.
- Stealth/audit branches intentionally suppress activity.
- Activity, notifications, domain events, and realtime are separate representations.
- Decoy changes the final target without a dedicated redirect-chain schema.
- `POWERUP_BLOCKED` and `POWERUP_USED` are different branches.
- Old and new event systems coexist.
- Transaction rollback can remove mutation and activity together; post-commit notification/realtime failures do not.
- Query filters and duplicate suppression can look like missing events.
- Team context must currently be reconstructed from participants.

### All Decoy-compatible power-ups

Targeting and redirect logic must be audited for `SHORTCUT`, `RED_CARD`, `WRONG_TURN`, `LEG_CRAMP`, `SIGNAL_JAMMER`, `LEECH`, `HITCHHIKE`, `QUICKSAND`, `RAINSTORM`, `PINECONE_TOSS`, and other target/AoE types governed by `powerupPolicy`, target-context validation, and `usePowerup.js`. `MIRROR` is relevant to reflection semantics. `COMPRESSION_SOCKS` and `UMBRELLA` are defensive interception effects. `IMPOSTER` is stealth-related and intentionally hidden from the feed.

### Edge cases

Redirect to attacker, attacker teammate, Decoy-owner teammate, already affected user, invalid/ineligible participant, forfeited user, completed/cancelled race, shield or umbrella interception, duplicate AoE landing, multiple Decoys, self-targeting, stealth effects, old client capabilities, retries, concurrent use, and race completion during execution all require explicit tests. Existing locks, conditional consumption, and retry/replanning logic are important correctness boundaries.

Legacy: `DAILY_COIN_LADDER = [10, 20, 30, 40, 50]` and `DAY_6_FALLBACK_COINS = 100`. Box amounts come from balance configuration and `dailyBoxOdds.js`; claim commands are authoritative.

The backend sends amount-bearing fields such as `coinAmount` for the legacy ladder and selected coin amounts in claim results. The likely failure is a frontend formatter that maps `COINS` to generic `Coins` without reading `coinAmount` or the fulfilled amount. Every label builder and result modal must be checked separately.

### Exact affected rewards

Potentially affected are fixed ladder tiles, Day 6 fallback, common/uncommon/rare coin segments, result modal, and any history/activity formatter. The exact affected surface must be confirmed by locating all `reward['type']`, `coinAmount`, and `coinsAwarded` reads in `daily_reward_screen.dart` and related widgets.

### Root cause

The backend already has amount fields. The defect is most consistent with legacy/new schema handling collapsing a coin reward to its type, or a result formatter reading the generic type rather than the fulfilled amount.

## F. Change 5 — Completed Pinned Races

### Current pinning architecture

Backend calls pins “favorites.” State is `RaceParticipant.favoritedAt`, not a separate table and not Redis-only. Tournament favorites use `TournamentParticipant.favoritedAt`.

### Database/schema representation

`RaceParticipant.favoritedAt` is nullable. Relevant indexes are `(userId, status)`, `(raceId, status)`, and `(userId, status, inviteExpiresAt)`. Race has status indexes including `(status)`, `(isPublic, status)`, `(seedId, status)`, `(tournamentId, status)`, and `(seriesId, status)`. The favorite column was added by `20260828190000_add_race_favorites_and_impact_attribution`.

### Read path

`getRaces`, `getFeaturedRaces`, race models, `raceListCache`, `raceListViewerCache`, `raceListReadBatch`, home launch reads, and Flutter `races_tab.dart` project favorite state into pinned sections.

### Write path

`PUT /races/:raceId/favorite` calls `setRaceFavorite`, which validates an accepted participant, sets or clears `favoritedAt`, preserves the timestamp for idempotent favorite=true, and invalidates race-list caches.

### Race-completion interaction

Completion uses `completeRace`, race-state resolution, resolution queues, deadline schedulers, and post-task workers. No inspected code proves that completion clears every participant’s favorite. The safer assumption for specification is that stale favorite rows can remain unless the read path filters completed races.

### Cache behavior

Favorite mutations invalidate race-list caches. Completion invalidates race-related caches, but a stale favorite flag can remain in the row or cached projection unless completed races are excluded.

### Realtime behavior

Event-driven refresh can refresh race data, but the pinned section only disappears if the refreshed list filters completed status, completion clears the favorite, or a dedicated frontend removal occurs.

### Existing indexes

There is no obvious composite index specifically for `(userId, favoritedAt, race.status)` or active favorite races. Existing user/status and race/status indexes support current reads but may not be optimal for a large pinned-only query.

### Current stale-state scenarios

If a pinned race completes while the app is closed, reopening can show it if the API returns completed favorites and Flutter only checks favorite state. In an open app, completion/realtime refresh does not guarantee disappearance unless the list projection or frontend filtering removes it.

### Comparison of read-filter vs completion-time cleanup approaches

| Approach | DB/cache effect | Cleanup | Stale behavior |
|---|---|---|---|
| Clear every participant on completion | Per-participant writes and per-user invalidation | None | No stale rows; large completion fan-out |
| Filter completed races on read | No completion fan-out; adds status/favorite query work | Rows remain | UI correct; preference persists |
| Read filter plus async cleanup | Correct reads plus bounded batch writes | Worker required | UI correct; storage eventually cleaned |

At millions of users, synchronous participant cleanup risks write amplification, locks, and cache storms. Read filtering or bounded asynchronous cleanup avoids that global fan-out.

### Existing tests

Backend: `pinned-races-section.test.js`, race finish/reward tests, race list/read-batch/cache tests, and Redis cache efficiency tests. Frontend: `races_tab_test.dart`, races-tab card/group/header/team tests, capacity parity tests, completed-race tests, event-driven refresh tests, and lifecycle polling tests.

### Missing tests

Closed-app completion, open-app realtime completion, completed favorite exclusion, team/tournament cases, cache-hit behavior, pagination, missing status compatibility, and bounded cleanup behavior.

### Scaling considerations

This is a read-path and race-completion design issue. Avoid per-participant completion writes and per-user cache invalidation unless explicitly required. Any read filter must be paginated and backed by an intentional index; any cleanup must be batched and coalesced.

## G. Change 6 — Team Chat Usage

### Current chat architecture

Frontend: `lib/services/race_chat_service.dart`, `lib/screens/race_detail_screen.dart`, and chat-related race detail widgets/tests.

Backend: `sendRaceMessage.js`, `deleteRaceMessage.js`, `setRaceChatMute.js`, `getRaceMessages.js`, `getRaceMessageStreams.js`, `raceMessage.js`, `raceMessagesCache.js`, race routes, notification handlers, and realtime/domain-event infrastructure.

### Database schema

`RaceMessage` contains `id`, `raceId`, `senderId`, `kind`, `body`, `createdAt`, `deletedAt`, `audience`, and `team`. `body` is capped at 500 characters. Indexes are `(race_id, created_at)`, `(race_id, audience, team, created_at)`, and the raw partial `race_messages_user_watermark_idx` on non-deleted messages.

### Realtime architecture

Messages use Redis race-message caches and shared event/realtime delivery. Team sends validate capability, race/team membership, accepted status, active status, and forfeit state. Sending also performs a 5-messages-per-10-seconds-per-user/race rate-limit count and acquires a race write fence for final validation.

### Existing analytics

The repository contains activation, foreground, notification-open, server activation, admin analytics, billing events, and logs. No verified dedicated chat-open, chat-read, reader, or retention instrumentation was found.

### Metrics available now

Persisted data directly provides messages, senders, races with messages, messages per race/user/team, timestamps, deleted state, and participant/race relationships. Notification/unread data may provide notification-side metrics if chat messages are projected there, but that should be verified separately.

### Metrics derivable from DB

Team races created, team races with messages, chat adoption rate, unique senders, messages per active chat, participant sender percentage, 0/1–5/6–20/21+ distributions, repeat users, and usage by race size are derivable from `races`, `race_messages`, and `race_participants`.

### Metrics requiring new instrumentation

Chat opens, impressions, closes, unique readers, read state, unread-to-read conversion, push-open attribution, messages per DAU, retention correlation, chat session duration, and platform/app-version breakdown require instrumentation.

```sql
SELECT r.team_size, COUNT(DISTINCT r.id) AS races,
       COUNT(DISTINCT CASE WHEN m.id IS NOT NULL THEN r.id END) AS used,
       COUNT(m.id) AS messages
FROM races r
LEFT JOIN race_messages m
  ON m.race_id = r.id
 AND m.audience = 'TEAM'
 AND m.deleted_at IS NULL
WHERE r.is_team_race = true
GROUP BY r.team_size
ORDER BY r.team_size;
```

The percentage and bucket queries should be finalized against exact enum casing and production-safe time predicates later.

### Storage/infrastructure cost

Chat creates one PostgreSQL row and indexed entries per message, Redis cache activity, realtime fan-out to race viewers, and possibly notification/unread/push work. Message body size is bounded. No dedicated chat cleanup job was confirmed in this investigation.

### Shared vs chat-specific infrastructure

Chat-specific: `race_messages`, chat queries/commands, message cache keys, team authorization, and chat notification content. Shared: PostgreSQL, Redis, realtime transport, domain events, notification delivery, device tokens, and analytics infrastructure. Removing chat would not remove most shared infrastructure.

### Scaling considerations

Message sends perform a rate-limit query and team sends use a race fence plus participant reload. Per-message notification/realtime fan-out, cache invalidation, hot active-race keys, and unbounded message retention are the main risks. Existing pagination and indexes are positive. Existing database data can measure many metrics without adding per-message analytics events.

## H. Cross-Cutting Architecture

### Bara Gold entitlement architecture

```text
App Store/Google Play -> RevenueCat -> webhook/provider sync
 -> BillingPurchase/BillingSubscription -> goldMembershipForUser
 -> backend catalog/reward authorization -> Flutter billing/UI state
```

RevenueCat orchestrates provider transactions; backend billing state authorizes application behavior. Subscription access uses `accessUntil`, provider status, and `givesAccess`. Restoration uses RevenueCat restore plus backend synchronization/reconciliation. Internal product IDs and setup documents still use Bara+.

### Race activity/event architecture

Major systems are `RacePowerupEvent` activity, `RaceMessage` chat/system timeline, domain events/outbox, notification projections, persistent inbox notifications, push attribution/delivery, realtime refresh, race-resolution events, and audit rows. One action can create several independently constructed representations, which is the core Decoy clarity problem.

### Race lifecycle/state machine

Primary transitions are `PENDING -> ACTIVE -> COMPLETED`, with cancellation paths from pending or active. Scheduled start/end, participant acceptance/forfeit, seeded windows, tournament state, resolution, payout, and post-completion notification are separate lifecycle dimensions. `Race.status` is the ordinary race status source of truth.

### Analytics architecture

Verified systems include activation analytics, foreground ingestion, notification-open analytics, server activation events, admin snapshots, RevenueCat billing records, and event/notification logs. No verified Firebase Analytics, Mixpanel, Amplitude, PostHog, Segment, or chat-open/read event was found.

### Shared caches/jobs/realtime systems

Caches cover race lists, viewer races, race progress, messages, user presentation, notification unread state, billing/frontend state, and admin snapshots. Workers cover race resolution, deadline/effect scheduling, notification release/reconciliation, billing reconciliation, device-token cleanup, analytics cleanup, placement transitions, and post-task cleanup.
